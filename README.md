# open-design 优选 IP

把 `open-design.ai` 及其 API 从 Cloudflare 的美国机房切到香港机房，解决国内访问慢、请求超时的问题。

## 问题

Cloudflare 用 anycast 分配机房，同一个域名在不同线路上会落到不同城市。国内很多线路默认被分到洛杉矶 LAX，国际链路丢包严重：

- 首页 387KB 传到一半就卡死，经常 20 秒超时
- API 请求十次有四次 TLS 握手直接超时
- 连纯边缘、不回源的 `/cdn-cgi/trace` 都要 2~6 秒

瓶颈在链路，不在源站。

## 效果

同一条宽带，`deepseek-v4.1-flash` 各请求 20 次实测：

| 指标 | 改前 LAX | 改后 HKG |
|---|---|---|
| 成功率 | 12/20 | **20/20** |
| 首字节延迟 | 2807ms | **1153ms** |
| 首 token 延迟 | 5646ms | **2125ms** |
| 端到端完成 | 12956ms | **2235ms** |

改前有 8 次直接超时，最慢一次拖了 62 秒；改后 20 次全部落在 1.8~5.2 秒内。

## 原理

`162.159.x` / `104.26.x` 这一段的 IP 会落到香港 HKG（60~100ms），比默认命中的 LAX 干净得多。脚本做的事：

1. 扫描 Cloudflare 官方 IP 段，并发测 TCP 延迟
2. 用 `/cdn-cgi/trace` 确认每个 IP 的真实落地机房，筛出香港节点
3. 对候选做**完整 HTTPS 实测**（带真实 SNI/Host，测 p50/p95），先淘汰再排序
4. 逐个域名用真实证书校验（能完成 TLS 握手即证明该 IP 持有合法证书）
5. 把选出的 IP 写进 hosts，只动一段带标记的内容

### 扫描分两段，为什么

**粗筛**：高并发（96）短超时（1s），只求把完全不通的 IP 筛掉。这里的 rtt 是 `min()` 出来的幸运值，**不能用于排序**。

**域名实测轮**：对粗筛前列的候选，带真实 SNI/Host 走完整 HTTPS 请求（TLS + 拿到首字节），默认 20 秒采样窗口，然后**先淘汰、再排序**：

- **淘汰**：任一域名的 p95 ≥ 999ms 即出局。999 是超时惩罚值，能达到说明该 IP 至少有 5% 的请求完全卡死 —— 这种 IP 不是"慢一点"，是"时断时续"，写进 hosts 后用户会随机遇到几秒卡死。
- **排序**：合格者按各域名 p50 的平均值。不拿 p95 做主排序键，因为它对个别超时过于敏感，会让排序结果随一次抖动跳变。

只测 TCP 握手会漏掉关键问题：TCP 能连上不代表 HTTPS 能通。实测中只做 TCP 的版本把这些 IP 选进推荐：

| IP | 只测 TCP 的判定 | 完整 HTTPS 实测 |
|---|---|---|
| `104.26.9.1` | 选为第 4 名 | **120 次请求全部失败** |
| `104.26.12.1` | 选为第 1 名 | 超时率 18%，p95 顶到 999ms |
| `104.26.0.1` | 选为第 3 名 | 超时率 37% |

## 用法

### 一键（推荐）

双击 `open-design优选IP.bat`，会自动申请管理员权限，然后扫描、校验、写入。

### 命令行

```bash
python cf_pin.py menu      # 交互式菜单
python cf_pin.py scan      # 只扫描不改动系统
python cf_pin.py apply     # 扫描并写入 hosts（需管理员）
python cf_pin.py status    # 查看当前状态与实测延迟
python cf_pin.py revert    # 删除写入的段，恢复原样
```

常用参数：

```bash
python cf_pin.py scan --full                     # 扫全部官方段（慢，兜底用）
python cf_pin.py apply --ip 162.159.129.1        # 指定 IP，跳过扫描
python cf_pin.py apply --domains open-design.ai  # 指定域名
python cf_pin.py apply --redundant 3             # 写几个备用 IP
python cf_pin.py apply --dry-run                 # 演练，不实际写入
```

## 候选池：为什么默认只扫两段

同一线路、同一时段，只改候选池大小实测：

| 候选池 | 候选数 | 有响应 | 前 12 个里近端机房 | 粗筛耗时 |
|---|---|---|---|---|
| 全部官方段 | 912 | 317 | 10 | 22s |
| 两段隔 4 取 1 | 128 | — | 8 / 段 | 4s |
| **两段隔 2 取 1（默认）** | **256** | — | **12 / 段** | **7s** |
| 单段扫满 | 256 | 136 | **12** | 5s |

关键结论：**多扫一倍收益为零** —— 单段扫满 256 个 /24 时近端候选仍是 12 个，因为这一段落能到近端的 IP 总共就这么多。所以默认只扫 `162.159.0.0/16` 和 `104.26.0.0/16`，各隔 2 个 /24 取 1，候选从 912 降到 256，速度提升约 3 倍。

`--full` 保留全量扫描作为逃生通道：链路状况变了、或关键段被阻断时仍有兜底。

抽样用等距而非随机：实测两者在统计上无法区分（近端 11~12 个，随机 8 个种子均值 11.75），但随机会让每次 scan 结果不可复现、出问题难排查。

## 关于延迟，需要说清楚一点

切换机房的收益是巨大的（见上表，2.5 倍）。但**在都落到 HKG 的 IP 之间**，差异很小。12 个 IP × 20 次真实推理请求实测：

- TTFT 全部落在 **698~884ms**，跨度 186ms，小于单次请求抖动
- token/s 全部落在 **304~327**，跨度仅 7%
- 延迟构成：`连接 70ms + TLS 81ms + 等待上游模型 1372ms`，其中上游占 **90%**

所以本工具能保证的是**"不选到坏 IP"**（避免 LAX 的丢包和卡死），而不是在同一机房内进一步压缩延迟。那 90% 的上游时间不是选 IP 能优化的。

## 注意

- **ping 不通是正常的。** 香港这些 IP 大多不回应 ICMP，`ping open-design.ai` 会超时，但网页和 API 走 TCP/TLS，不受影响。用 `python cf_pin.py status` 看真实延迟。
- **浏览器开了 DoH 会绕过 hosts。** 如果配好了还是慢，去浏览器设置里关掉「安全 DNS」。
- **需要被优化的是 API 域名。** open-design 客户端的 API 走 `amr-link.open-design.ai`，只改主域名没用。
- **IP 会失效。** 运营商路由或机场线路变化后，重跑一次 bat 重新优选即可，属于正常现象。
- **hosts 没有真正的故障转移**：只有当前面的 IP 超时（约 21 秒）才会尝试下一个，所以默认只写 2 个（`--redundant 2`），写多了只是让文件臃肿，并不会更快。

## 安全

- 写入前备份原 hosts 为 `hosts.bak.<时间戳>`
- 只修改带 `CLOUDFLARE-PIN` 标记的那一段，其余内容一字不动
- 写入前逐个域名校验证书，校验不过不写
- 原子替换失败时自动退化为原地重写，不会留下半截文件
- 一条命令还原：`python cf_pin.py revert`

## 环境

Windows（改写 hosts 需要管理员权限），Python 3.8+，无第三方依赖。
