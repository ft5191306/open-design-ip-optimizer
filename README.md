# open-design 优选 IP 工具

为 `open-design.ai` 与 `amr-link.open-design.ai` 挑选延迟最低的 Cloudflare 边缘 IP，
写入 hosts 让这些域名落到香港（HKG）机房，而不是被 anycast 甩到洛杉矶（LAX）。

## 为什么需要它

Cloudflare 用 anycast，同一个域名在不同线路上会落到不同机房。国内很多线路默认被甩到
LAX，国际链路严重丢包：

- `open-design.ai` 首页 387KB 要 5~53 秒，TLS 握手 15~25 秒后超时
- `amr-link.open-design.ai` 的 API `/v1` 直接超时。连纯边缘、不回源的
  `/cdn-cgi/trace` 都要 2~6 秒 —— 瓶颈在链路，不在源站

而 `162.159.x` / `104.26.x` 这一段会落到 HKG（香港）：TCP 60~70ms，
首页 0.3 秒、API 0.43 秒，成功率 100%。

## 用法

双击 `open-design优选IP.bat`（会自动申请管理员权限，改写 hosts 需要）。

命令行：

```bash
python cf_pin.py scan              # 扫描优选 IP，不改动系统
python cf_pin.py scan --full       # 扫全部 Cloudflare 官方段（慢，兜底用）
python cf_pin.py apply             # 写入 hosts
python cf_pin.py apply --dry-run   # 演练，不实际写入
python cf_pin.py status            # 查看当前状态与实测延迟
python cf_pin.py revert            # 删除本工具写入的 hosts 段
python cf_pin.py menu              # 交互式菜单
```

只改 hosts 里一段带标记的内容，其余内容一个字都不动：

```
# >>> CLOUDFLARE-PIN BEGIN (managed by cf_pin.py) >>>
...
# <<< CLOUDFLARE-PIN END <<<
```

每次写入前自动备份原始 hosts，`revert` 可一键还原。

## 扫描流程

分两段，因为这两段要解决不同的问题：

**1. 粗筛**：高并发（96）短超时（1s），只求把完全不通的 IP 筛掉。
这里的 rtt 是 `min()` 出来的幸运值，**不能用于排序**。

**2. 域名实测轮**：对粗筛前列的候选，带真实 SNI/Host 走完整 HTTPS 请求
（TLS + 拿到首字节），默认 20 秒采样窗口，然后**先淘汰、再排序**：

- **淘汰**：任一域名的 p95 ≥ 999ms 即出局。999 是超时惩罚值，能达到说明
  该 IP 至少有 5% 的请求完全卡死 —— 这种 IP 不是"慢一点"，是"时断时续"，
  写进 hosts 后用户会随机遇到几秒的卡死。
- **排序**：合格者按各域名 p50 的平均值。不拿 p95 做主排序键，因为它对
  个别超时过于敏感，会让排序结果随一次抖动跳变。

## 实测依据

### 候选池：912 → 256

同一线路、同一时段，只改候选池大小：

| 候选池 | 候选数 | 有响应 | 前 12 个里近端机房 | 粗筛耗时 |
|---|---|---|---|---|
| 全部官方段 | 912 | 317 | 10 | 22s |
| 两段隔 4 取 1 | 128 | — | 8/段 | 4s |
| **两段隔 2 取 1（默认）** | **256** | — | **12/段** | **7s** |
| 单段扫满 | 256 | 136 | **12** | 5s |

关键结论：**多扫一倍收益为零** —— 单段扫满 256 个 /24 时近端候选仍是 12 个，
因为这一段落能到近端的 IP 总共就这么多。所以默认只扫 `162.159.0.0/16` 和
`104.26.0.0/16`，各隔 2 个 /24 取 1。`--full` 保留全量作为逃生通道。

抽样用等距而非随机：实测两者统计上无法区分（近端 11~12，均值 11.75），
但随机会让每次结果不可复现、出问题难排查。

### 为什么必须做完整 HTTPS 而不是只测 TCP

对比过一个只做 2 次 TCP 握手的旧实现：

| IP | 旧实现判定 | 完整 HTTPS 实测 |
|---|---|---|
| `104.26.9.1` | 选为第 4 名推荐 | **120 次请求全部失败（100%）** |
| `104.26.12.1` | 选为第 1 名推荐 | 超时率 18%，p95 顶到 999ms |
| `104.26.0.1` | 选为第 3 名推荐 | 超时率 37% |

旧实现选出 12 个 IP，其中 5 个带硬超时；本实现 0 个。原因：TCP 能连上不代表
HTTPS 能通，而其 rtt 取两次的 `min()`，天生会把"间歇性丢包"测成"最快"。

## 重要：延迟的真实构成

用流式请求（TTFT + token/s）实测了 12 个 IP × 20 次真实推理请求：

```
连接 70ms + TLS 81ms + 等待上游模型 1372ms = 1523ms
                                        ↑ 占 90%
```

- 12 个 IP 的 TTFT 全部落在 **698~884ms**，跨度 186ms，小于单次请求抖动
- 12 个 IP 的 tok/s 全部落在 **304~327**，跨度仅 7%
- 上游模型那 90% **不是选 IP 能优化的**

所以：**本工具能保证的是"不选到坏 IP"，不是"让模型更快"。**
在这条线路上，任何 IP 优选都无法显著降低推理延迟。

## 依赖

- Python 3.8+（只用标准库，无需 pip 安装）
- Windows（改写 hosts 需要管理员；Linux/macOS 下逻辑同样可用，但未经测试）

## 注意

- 香港机房的这些 IP 多数不回应 ICMP，所以 `ping cloudflare.com` 会显示超时 ——
  这是正常现象，网页访问走 TCP/TLS 不受影响。
- 浏览器如果开了「安全 DNS / DoH」，会绕过 hosts。需要在浏览器里关掉。
- hosts 没有真正的故障转移：只有当前面的 IP 超时（约 21 秒）才会尝试下一个，
  所以默认只写 2 个（`--redundant 2`），写多了只是让文件臃肿，并不会更快。
